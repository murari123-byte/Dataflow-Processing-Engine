# DataFlow Processing Engine

An end-to-end PySpark data engineering platform built with Python and Docker. It generates customer and order datasets, validates and transforms records, builds analytical and dimensional models, and includes monitoring, reconciliation, automated testing, and performance benchmarks.

## 1. Project Overview

The pipeline processes two input datasets:

- **Customers:** `customer_id`, `customer_name`, `city`, `signup_date`
- **Orders:** `order_id`, `customer_id`, `product_id`, `quantity`, `unit_price`, `order_ts`

The workflow covers ingestion, schema and business validation, rejection handling, enrichment, daily aggregation, dimensional-model construction, reconciliation, staged publishing, monitoring, and analytics.

### Key Features

- Reproducible sample and large dataset generation.
- Schema validation and business-rule checks.
- Duplicate detection and rejected-record quarantine.
- PySpark transformations and daily sales aggregation.
- Fact and customer/product dimension datasets.
- Parquet publishing with staging and rollback protection.
- Run monitoring and reconciliation reports.
- SQL-based analytical queries.
- Automated tests using Pytest.
- Baseline/optimized aggregation and join benchmarks.
- Docker-based Spark execution.

## 4. Pipeline Architecture

```text
CUSTOMERS CSV             ORDERS CSV
      |                       |
      +-----------+-----------+
                  |
              INGESTION
                  |
          SCHEMA VALIDATION
                  |
         BUSINESS VALIDATION
                  |
          +-------+-------+
          |               |
     VALID ORDERS     REJECTED ORDERS
          |               |
          |           QUARANTINE
          |
       ENRICHMENT
          |
    DAILY AGGREGATION
          |
    DIMENSIONAL MODEL
          |
   +------+------+------+
   |             |      |
 FACT ORDERS  CUSTOMER  PRODUCT
              DIMENSION DIMENSION
          |
     RECONCILIATION
          |
   STAGED PARQUET PUBLISHING
          |
   ANALYTICS AND REPORTS

   MONITORING RECORDS EACH RUN
```

### Pipeline Stages

1. **Data generation:** Create deterministic sample and large CSV datasets.
2. **Ingestion:** Read customer and order data with PySpark.
3. **Validation:** Check required columns, values, timestamps, duplicates, and customer references.
4. **Classification:** Separate valid orders from rejected records and retain rejection reasons.
5. **Transformation:** Derive order date and total amount, then aggregate daily product sales.
6. **Dimensional modeling:** Build `fact_orders`, `dim_customers`, and `dim_products`.
7. **Reconciliation:** Check input classification and aggregation consistency.
8. **Publishing:** Stage and publish six Parquet datasets.
9. **Monitoring:** Record run status, timing, record counts, and errors.
10. **Analytics:** Run analytical queries against published datasets.

## 6. Validation Rules

The pipeline checks:

- Required input columns and expected schema.
- Missing order IDs, customer IDs, and product IDs.
- Customer references that do not exist in the customer dataset.
- Missing, invalid, or non-positive quantities.
- Missing, invalid, or negative unit prices.
- Missing or malformed timestamps.
- Duplicate order IDs.

Rejected records are written separately with source information and rejection reasons. A record can have multiple rejection reasons, so the total number of reasons can exceed the number of rejected records.

## 7. Transformations and Published Datasets

The pipeline publishes six Parquet datasets.

| Dataset | Grain / purpose |
|---|---|
| `valid_orders` | One row per accepted order, with validated source fields |
| `daily_sales` | One row per order date and product |
| `rejected_orders` | One row per rejected input record, with rejection reason(s) |
| `fact_orders` | One row per valid order |
| `dim_customers` | One row per unique customer ID |
| `dim_products` | One row per product ID present in valid orders |

### Fact and Dimension Model

The dimensional model uses source identifiers as keys:

- `fact_orders.order_id` is the fact-table key.
- `fact_orders.customer_id` references `dim_customers.customer_id`.
- `fact_orders.product_id` references `dim_products.product_id`.
- The fact grain is one row per valid order.
- `total_amount` is calculated as `quantity * unit_price`.
- `dim_products` currently contains only `product_id`, because product descriptions and categories are not available in the input.
- Customer and product dimensions are built from the supplied customer data and valid orders respectively.

The model does not currently include a separate date dimension or product attributes that are absent from the source data.

See [`docs/data_dictionary.md`](docs/data_dictionary.md) for output schemas, data types, keys, grain, and business rules.

### Daily Sales Aggregation

`daily_sales` contains:

- `order_date`
- `product_id`
- `total_orders`
- `total_quantity`
- `total_revenue`
- `average_order_value`

## 8. Analytical Queries

The analytics module runs five SQL-based queries:

1. **Revenue by Product:** Orders, quantity, and revenue for each product.
2. **Daily Revenue:** Daily order counts and revenue.
3. **Top 10 Products:** Products ranked by revenue.
4. **Sales Summary:** Overall orders, quantity, revenue, and average order value.
5. **Rejection Summary:** Rejected record counts grouped by validation reason.

Results are written under `reports/analytics/`.

Run analytics after the pipeline has published its outputs:

```powershell
docker run --rm `
  -v "${PWD}:/workspace" `
  -w /workspace `
  -e PYTHONPATH=/workspace `
  yottaflex-spark `
  /opt/spark/bin/spark-submit src/run_analytics.py
```

## 9. Monitoring and Reconciliation

### Monitoring

Each execution records a unique run ID, start and finish timestamps, duration, status, input/valid/rejected counts, aggregation group count, and error details when applicable.

Run history is appended to:

```text
reports/pipeline_runs.jsonl
```

### Reconciliation

The pipeline checks:

**Input classification**

```text
Input Records = Valid Records + Rejected Records
```

**Aggregation**

```text
Aggregated Orders = Valid Records
```

The reconciliation report is written to:

```text
reports/reconciliation_report.json
```

The pipeline stops if reconciliation fails, before publishing new output datasets.

## 10. Safe Publishing, Reruns, and Recovery

The publisher uses a staging-and-backup process for all six datasets:

1. Write each new dataset to a temporary staging directory.
2. Move existing output directories to backup locations.
3. Move staged datasets to their final locations.
4. Remove backups after successful publication.
5. On a publishing exception, remove newly published outputs and attempt to restore previous outputs.

This protects previous outputs against normal publishing and staging failures. It is not a fully atomic transaction across all output directories if the machine or process crashes during commit.

### Retry, Restart, and Backfill

- **Retry:** After correcting an input or resolving an execution issue, rerun the main pipeline using the intended input files.
- **Restart:** Start the pipeline again with the normal Docker command. The publisher stages new outputs and attempts to restore previous outputs if a publishing operation fails.
- **Backfill:** To process historical records, include the required historical records in the input datasets and rerun the batch pipeline.
- **Late and out-of-order records:** Batch processing groups records using their order timestamps, so input row order does not determine aggregation results.

The current implementation is batch-oriented. It does not implement streaming watermarks or automatic incremental backfills.

## 13. Performance Benchmarks

Benchmarks compare baseline and optimized implementations using the same generated dataset and Docker-based Spark environment. The aggregation benchmark uses a warm-up and three measured iterations. The join benchmark disables automatic broadcast selection so the standard join and explicit broadcast join can be compared.

### Aggregation Benchmark

| Metric | Baseline | Optimized |
|---|---:|---:|
| Iteration 1 | 4.291 s | 1.077 s |
| Iteration 2 | 3.249 s | 0.982 s |
| Iteration 3 | 3.259 s | 0.745 s |
| Median | 3.259 s | 0.982 s |

**Median execution-time improvement: 69.86%.**

The run processed 100,050 input rows: 99,500 valid and 550 rejected. The baseline and optimized results matched.

The optimized aggregation uses repartitioning and persistence. These techniques can help for the tested workload, but their benefit depends on data size, partitioning, memory, and cluster resources.

### Join Strategy Benchmark

| Metric | Standard sort-merge join | Explicit broadcast join |
|---|---:|---:|
| Iteration 1 | 0.423 s | 0.329 s |
| Iteration 2 | 0.407 s | 0.329 s |
| Iteration 3 | 0.622 s | 0.286 s |
| Median | 0.423 s | 0.329 s |

**Median execution-time improvement: 22.06%.**

The standard plan used a `SortMergeJoin`; the explicit broadcast plan used a `BroadcastHashJoin`. The customer lookup still requires deduplication, and the broadcast strategy is appropriate only when the lookup data fits safely in executor memory.

These measurements are specific to the tested local Docker environment, input dataset, and three measured iterations. They are not guarantees of performance on other hardware or workloads.

See [`docs/performance_benchmark.md`](docs/performance_benchmark.md) for methodology, physical-plan observations, and limitations. Benchmark result files are stored under `reports/`.

## 14. Design Decisions and Limitations

### Design Decisions

- PySpark DataFrames are used for validation, transformation, and analytics.
- Parquet is used for processed datasets.
- Validation, transformation, dimensional modeling, monitoring, reconciliation, and publishing are separated into modules.
- Reconciliation runs before publishing.
- Run history is stored in JSONL format.
- Staging and backups provide rollback protection for normal publishing failures.
- Docker provides a reproducible Spark runtime.

### Current Limitations

- Spark runs locally inside Docker; the project is not deployed to a distributed cluster.
- Input data is generated CSV data.
- Processed datasets are stored locally in Parquet format.
- The product dimension contains only product IDs because product attributes are not available in the source.
- There is no separate date dimension.
- Multi-dataset publishing is not crash-atomic across all output directories.
- The batch pipeline does not implement streaming watermarks or automatic incremental backfills.
